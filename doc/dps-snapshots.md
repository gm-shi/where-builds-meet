# 秒伤回归快照

`npm run test:dps` 会将每个非空的模板循环（包括开发中流派的循环）与 `tests/snapshots/rotation-dps.json` 进行比较。发布部署工作流会在发布前运行这项防护检查，手动部署也不例外。普通构建、测试、监听模式以及 PR/main CI 不执行已接受秒伤的比较，但保留其覆盖率、选择器和比较算法测试。

## 测试夹具选择

`tests/helpers/dps-snapshot-fixtures.ts` 从每个流派现有的循环目录中发现循环 JSON 文件，并发现同一配装组中的每个配装 JSON。每个非空循环都会与该组中的每个配装配对，并在破阵 18 和 19 下计算，其中包括武器配置不同的配装。生产计算包使用配装中配置的武器以及循环中记录的动作。用例使用稳定的 `<pathId>/<rotationId>/<buildId>/<breakthrough>` 键，因此更改流派的默认配装不会改变快照用例目录或计算输入。空的规划器循环会被排除。覆盖率测试会独立枚举配装/循环的交叉组合。发布防护检查会检测缺失和过时的基线键。循环与流派的更新选择器会包含所有匹配的配装；在选择器中带上配装 ID 则只选中该配装的用例。

2026 年 10 月 21 日，用户批准将覆盖范围扩展到每一个配装/循环组合，并接受其当前计算值。这取代了先前的默认配装用例以及仅针对霖的额外配装用例。共享的行为测试夹具加载器仍然选择默认配装和循环中显式的配装覆盖；只有发布用例加载器会扩展到全部配装。

当前快照计算使用破阵 18 和 19、每个循环保存的延迟（默认 40 ms；威为 30 ms）、涮鱼、天工·火、无帖，且不使用全局或技能覆盖值。循环提供其动作和战斗场景标记；配装提供其武器、装备、心法和套装。测试夹具会传入 `src/application/graduation.ts` 的 `buildPresetRotationBundle` 和 `calculateRotationBaseline`，即生产环境所用的计算流水线。检查中不会引入任何浏览器偏好设置或重复的伤害公式。

共享的循环测试夹具加载器为现有的行为测试保留破阵 17 的默认值。`loadDpsSnapshotCases` 会为发布防护检查及其覆盖率检查显式选择 18 和 19；该默认值无法决定快照环境。

## 已接受数值与审核关卡

2026 年 10 月 26 日，用户接受了破阵 18 和 19 下敌方防御从 446 修正为 500，并批准刷新全部 222 个模板基线。更高的敌方防御使秒伤和总伤害降低 0.95–1.50%，持续时间不变。例如，`bamboocutDust/dust-dummy-1-min-100pc/dust-full-min/18` 从 78,106.31550827304 秒伤变为 77,037.10483776833 秒伤。此修正不改变敌方等级、判定抗性和气血。

按照要求，当前基线集以破阵 18 和 19 下的四十个用例取代了二十个破阵 17 用例。它们使用修正后的破阵固定奖励，以及各等级的装备、强化、武库、套装、心法和武学天赋。除非另有说明，本文档中较早的数值验收记录描述的是历史上的破阵 17 基线；快照 JSON 包含当前的确切数值。

2026 年 10 月的影版本发布对所有模板采用经用户批准的当前伤害。其中包括新的开发中影循环、按武器区分的卸势时机、战斗前的耐力恢复，以及已批准的虹真气与威防御对齐修复。快照 JSON 记录了确切的已接受数值。

Schema 版本 2 取代了旧的每个流派一个用例的文件。每个用例记录其测试夹具、秒伤、总伤害、秒疗、治疗总量和持续时间。秒疗和治疗总量直接取自生产计算的指标。没有治疗的用例在这两个字段中均记录为零。出现以下情况时，关卡检查失败：

- 秒伤、总伤害、秒疗、治疗总量或持续时间出现超过 4 个末位单位的任何变化，每个循环独立判断，增减两个方向均计。
- 循环覆盖缺失或被移除。
- 配装、循环、武学组合或固定环境发生变化。
- 秒伤、伤害或持续时间为非有限值、零或负数。
- 秒疗或治疗总量缺失、为非有限值或负数。

容差以 ULP（末位单位）而非百分比计算，因为伤害流水线是逐位确定的：它只使用精确定义的 IEEE-754 运算，以固定的单线程顺序累加，且不接受任何依赖区域设置、时间或随机数的输入。因此，相同的输入必须重现完全相同的位。4 个 ULP 足以吸收求和重结合或引擎变化带来的一次表示偏移，同时会拒绝每一个真实的变化；而 1% 的容差带宽约为 8x10^11 个 ULP，曾悄无声息地接受了未经审核的修改。五个存储的数值都会参与比较，且变化是相对于最近一次已接受的数值累积计算，而不是相对于上一次测试运行。

应用户要求，扩展的非霖基线保留了本次会话中延迟、时机和模板改动之前的数值。它们是使用修订版本 `f13eee3e2c6bc5b1a547a54bff7679110418fdf9` 中的循环和技能数据、在零延迟下重建的。在为鸢、威和钧补充更多循环之前，生产计算器已精确重现了它们现有的已接受基线。这些测试夹具的延迟被显式设为 0；与当前 40 ms 的环境比较时会有意标记为环境变化，直到每个新结果都经过审核。

四个霖循环则全部使用经用户批准的当前数据和 40 ms 延迟。「万物组队」先前的已接受数值被精确重现。这些数值涵盖了太白的时机变化、对齐后的卸势、修订后的奇术时机，以及（如有）起手时的万物为锋等待时间。现有的霖验收结果得以保留。

## 更新已审核的循环

运行 `npm run test:dps`，说明每个受影响循环的新旧结果及其原因，并在更新前获得认可。`DPS_UPDATE_IDS` 接受精确的用例 ID、用于同时选中两个破阵等级的 `<pathId>/<rotationId>` 前缀、用于选择该流派全部循环与破阵等级的流派 ID，或 `all`。未被选中的基线保持不变；未知或相互重叠的选择器会导致失败。

在 PowerShell 中：

```powershell
$env:DPS_UPDATE_IDS = "bamboocutKite/dummy-1-min-iv-bp"
try {
  npm run snapshots:dps:update
} finally {
  Remove-Item Env:DPS_UPDATE_IDS
}
```

在 POSIX shell 中：

```sh
DPS_UPDATE_IDS="silkbindDeluge" npm run snapshots:dps:update
DPS_UPDATE_IDS="stonesplitStrength/pure-dummy-1-min stonesplitMight/dummy-1-min" npm run snapshots:dps:update
```

仅在每个当前循环都已被接受后才使用 `all`；它还会移除过时的基线键。发布检查期间不要设置该变量。发布前请检查生成的差异，并运行格式化、构建和发布快照检查。当时机或增益的改动可能在总秒伤中相互抵消时，仍需进行针对性的机制测试。
